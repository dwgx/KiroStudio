# KiroStudio 工作流规范（WORKFLOW）

> 2026-08-15 定稿。本文件是**我们自己的工作流**——从 W1-W6 实战提炼，不是照搬任何
> origin/参考仓的定义（它们的 CLAUDE.md/CI/skills 只是形式参考，语义以本文件为准）。
> 适用：主会话 + 所有 subagent。与 CLAUDE.md（长期约束）、STATUS.md（状态入口）并列。

## 0. 铁律（最高优先级）

1. **用户最新明确指令 > 一切**（计划/skill/早期指令）。用户说停就停。
2. **证据优于自信**：agent 说完成 ≠ 完成。核验后再采信（见 §6）。
3. **改动最小**：修 bug 就修 bug，不顺手重构。每行改动可追溯到请求。
4. **诚实报告**：没跑过的命令不说跑过；验证不了就说验证不了；空返回 = 失败要重派。
5. **禁止 git add/commit/checkout/stash/reset/fmt**（多会话并发工作树）；快照走临时 index
   （CLAUDE.md 验证循环）。CI 快照分支可覆盖，但每波建议用 plumbing 建轻量 tag 保留。
6. **凭证纪律**：先读 `~/.claude/SECRETS.md`，值绝不 echo/写文件/进 commit；派 subagent
   处理凭证时 prompt 里带这条。

## 0.5 两类权威分级（v2 吸收 origin 10-covenant + 行业共识，2026-08-16）

同一问题永远只按一套顺序判断，两类问题分开：

**A. 行为事实（"现在代码/线上是什么样"）**
1. 可复现执行：当前 commit 上的确定性测试、探测、实测输出（服务器 CI、nbus 实查）
2. 当前代码 + 测试，配合 git log/blame（意图或时序存疑时）
3. 状态文件（STATUS/state/CURRENT）——**先核对日期再信**，且具体断言要对当前代码复核
4. 架构/协议/研究报告等叙述性文档（行号/行为描述会漂移，是弱证据）

**B. 规范决策（"应该怎么做"）**
1. owner 当前明确指令（最新优先）
2. 本 WORKFLOW（宪法）
3. 已接受的决策记录（ISSUES.md (d) 带 superseded 链）
4. 设计文档（model-compat/quota-402 等）；冲突时不得静默选方便的，显式按已接受决策或请求 owner 裁决

**推论**：计划/研究结论**永远不会因为写得详细就变成事实**——落地必须过执行 + 验证。这是"证据优于自信"的显式化。

## 0.6 验证分级（v2 吸收，2026-08-16）

| 级 | 形式 | 用途 |
|---|---|---|
| L1 | 写代码时 prompt 内自检 / 编译推演 | 迭代期最小检查 |
| L2 | 单测 + 守卫（needle 本地验证命中） | 单元行为钉死 |
| L3 | 服务器 CI（skiapi Docker 全量） | 确定性门控——交付前必过 |
| L4 | 独立核验（核验 agent 三态对照声明） | "干活的人不给自己打分" |

每波至少 L2+L3；声称"完成/修复/上线"必须有 L3 以上证据。**集成闭环检查**：新函数必问"谁调用它？链路端到端通吗？"（stats_stale 三次"set 无人调"的教训——单测绿 ≠ 系统工作）。

## 0.7 review 限幅（v2 吸收 Anthropic 官方警告，2026-08-16）

对抗 review 是找真问题，**不是为找茬而找茬**：reviewer 输出必须每条带"触发条件 + 证据 + 修法"，纯风格意见归 MINOR 不阻塞；避免"发现 30 条但没有一条能复现"的过度工程式 review。review 发现 MINOR 时**立即闭环**（修掉或显式登记），不攒到用户问。

## 1. 任务生命周期（每个任务走完这 9 步）

```
需求澄清 → 目标定义 → 计划 → 执行(派发) → 自review → 落实核验 → 主线review → CI → 文档同步
     ↑ 模糊就问(带选项)  ↑ 交付物/验收/非目标  ↑ 每agent自检    ↑ 声明vs代码  ↑ 对抗找茬   ↑ 服务器实测  ↑ 六件套
```

1. **需求澄清**：开工前恢复真实目标。模糊就追问（一次问清，带选项+推荐）；能自己查清的
   自己查（仓库/git 状态/线上）。不假设、不默默挑解读。
2. **目标定义**：写清交付物、验收标准、非目标。重要任务先向用户复述确认。
3. **计划**：非平凡任务先写计划（目标/步骤/每步验收/风险）。计划是假设不是合同——探索
   推翻就改，记录为什么改。
4. **执行**：按 §2 派发纪律。小而明确直接做（编排在小题上是净亏）。
5. **自 review**：每个 subagent 交付前必须自检（§4 清单），输出含自 review 结论。
6. **落实核验**：每波完成后派核验 agent，对照声明逐项三态核对（✅/⚠️/❌），未落实的
   派补齐。**核验报告进 DONE.md**。这是防「声称做了没做」的常态机制（§6）。
7. **主线 review**：重要改动交付前派对抗 reviewer（给原始目标/验收/diff/证据，不给作者
   自辩）。BLOCKER/MAJOR 修掉再交付。
8. **CI**：服务器 Docker 验证循环（本机 8GB 编不过）。判定标准 `NNNN passed; 0 failed`；
   新增测试按名单跑一次确认执行。
9. **文档同步**：波次结束立即同步六件套（§7），不许攒。

## 2. 派发纪律（实测血泪，全部踩过）

| 规则 | 原因 |
|---|---|
| **执行类并行 ≤5**（探查类放开），嵌套 ≤3 层；每波派发前查在跑 agent | 8GB 机器物理上限，跑挂过 |
| **按文件边界划分**，同文件任务串行或合并 | A1+B1 同改 provider.rs → Self:: 缺前缀编译失败 |
| **上下文现编**：给足最小充分上下文（目标/问题/已确认事实/文件路径/约束/非目标/输出/证据要求/验收），不倒整仓 | subagent 不继承主会话知识 |
| **派发理由 = 信息增益**（独立信息/降不确定/竞争假设/独立 review），不为显得周全造冗余 | 浪费就是浪费 |
| **空返回 = 失败**：重派或自己核，不许当成功记 | k2cc 深挖第一轮空返回 |
| **验证声明要复核**：环境缺失时明确"验证不了" | 前端 agent 缺 node_modules 虚报 37/37 |
| 探查用 @explore、研究用 @general、查 bug 用 @debugger、审查用 @reviewer | 各司其职 |
| 修 bug 默认派 @debugger 不肉搏；同问题第二次失败必须换方法 | 同 bug 修 5-6 轮的血泪 |

## 3. 守卫纪律（本仓特有，踩过 5 次以上）

- **needle 运行时拼接**（`format!("a{}", "_b")`），防 include_str 读到测试自身字面量。
- **注释/文档里不写被守卫代码的完整字面量**（注释写标记字面量 = 守卫静默绿）。
- **测试段截断**：`split_once("\n#[cfg(test)]")` 或按函数锚切生产段。
- **拼接后验证命中**：交付前本地 `rg`/模拟确认 needle 唯一命中生产代码（B1 的
  `last_mapped_model= mapped_model` 缺空格 ×2 就是没验证）。
- **守卫的断言要真**：删掉被守卫目标会红（"删目标必红"是验收标准）。
- **行号漂移常态化**：工作树改动大，CURRENT.md 守卫清单每波核验时刷新行号
  （曾漂移 +4~+770）。

## 4. subagent 自 review 清单（交付前必过）

1. 功能正确性：实现与声明一致？边界（空/大小写/超长/并发）？
2. 同规则性：预判/改写/统计/黑名单各处判定是否同一函数同一规则？（模型链路教训）
3. 守卫兼容：改动区域有没有守卫？needle 是否会被新代码误命中/破坏？
4. 防自弱化：测试断言是精确值还是摆设？删目标会红吗？
5. 编译推演：签名/类型/借用/可见性逐项核对（本机编不过，只能推演）。
6. 文件范围：没碰并行 agent 的文件？没碰分配外的文件？
7. 诚实：没跑的命令/没验的项明确说，不写"逻辑自洽"蒙混。

## 5. 验证循环（CLAUDE.md 有完整命令，这里是判定要点）

- 快照：`git add -A -- src admin-ui build.rs Dockerfile`（统一命令，三份文档逐字一致；前端改动进快照，Dockerfile 自动构建内嵌）。
- **部署前核验**：`scripts/verify-snapshot.sh /tmp/kv.tar`（archive 后 scp 前必跑；src/、admin-ui/
  下未跟踪 `??` 文件必须已进快照，缺失即失败退出——历史两轮前端 BLOCKER 根因）。
- 判定：`test result: ok. NNNN passed; 0 failed`；build 失败看 `/tmp/b.log`
  （`grep -E "error\[E|^error"`）。
- 新增/改测试**按名单跑**（`cargo test --no-default-features <名> | tail -4`），确认
  真执行了（不是被 filter 吞）。
- 网络抖动（docker registry 拉语法镜像失败）会假失败——重试一次再判。
- **部署前**：本地 pnpm install 跑前端 tsc + node tests（node_modules 已可装，镜像可用）。

## 6. 落实核验机制（2026-08-15 建立，每波必做）

- 每波完成 → 派核验 agent（对照声明清单逐项读代码，三态表 ✅/⚠️/❌，只报有把握的差异）。
- 核验范围：该波全部声称项 + 守卫清单抽 10-15 条（守卫消失 = 防回退失效，最高优先）。
- 未落实/半落实 → 派补齐 agent（给差异清单）→ 主线复核 → CI。
- 核验报告进 DONE.md（声明 → 证据 → 三态）。W2-W6 已核验一轮：零未落实，抓出
  守卫行号漂移 + i18n 死键 107 个已清。

## 7. 文档六件套（职责与同步时机）

| 文件 | 职责 | 更新时机 |
|---|---|---|
| `STATUS.md`（仓根） | 当前状态入口：HEAD/工作树/线上/波次摘要/遗留/下一步 | 每波结束（含线上状态变更） |
| `CLAUDE.md` | 长期约束（推哪里/构建/部署/硬约束/历史事故） | 事实过时时（版本/部署流程变了就改） |
| `.claude/CONTEXT.md` | subagent 背景（读文件顺序/关键坑/验证/部署/参考仓） | 部署形态/参考仓变化时 |
| `.claude/state/CURRENT.md` | 会话状态 + **守卫清单**（行号每波核验刷新） | 每波结束 + 守卫行号漂移时 |
| `.opencode/ISSUES.md` | a-e 问题清单（含移植候选研究结论） | 每波结束同步（已完成项标记） |
| `.opencode/DONE.md` | 已完成工作 + 真实证据（核验报告落盘处） | 每波核验后 |
| `.opencode/state.md` | 波次记录（压缩恢复锚点） | 每波结束 |

同步纪律：**波次结束立即同步，不许攒**（曾多次"已修还标待做"的滞后）。

## 8. 参考仓使用纪律（2026-08-15 定）

- 参考仓（/tmp/ref-zyphr、/tmp/ref-k2cc）**只是参考**：研究它们的机制/问题/教训，
  **不照搬它们的定义与语义**（用户明示：不要理解 origin 干的事情的定义）。
- 移植前：研究（他们怎么做 + 我们现状 + 价值排序）→ 对抗评审（可行性/风险/与现有
  机制冲突）→ 才实现。评审否决项记录到 ISSUES (d)（fingerprint break、rotation_bias、
  链式映射等已否决）。
- 他们的问题是我们的反面教材（zyphr 日志泄漏 Authorization、k2cc fingerprint 生产死代码等）。

## 10. 常见失败模式（本仓踩过的坑，写代码/派发时对照）

1. 守卫 needle 拼接缺空格/形态不匹配（×3）→ 交付前本地模拟验证。
2. 并行 agent 改同文件 → Self::/覆盖冲突 → 按文件边界派发。
3. 线上配置字段 camelCase vs 代码 snake_case 误读（×2）→ 读配置先 `jq keys`。
4. 测试构造被 `MultiTokenManager::new()` 内启动逻辑抢先（跨月恢复）→ new 后手动重置。
5. Duration::abs 不存在 / chrono with_ymd_and_hms 需 TimeZone trait → 用 abs_diff / day0()。
6. 注释/文档写守卫字面量 → 静默绿（最危险，×5）。
7. `{e}` 在 format! 里是命名捕获语法 → E0425；测试消息里转义 `{{e}}`。
8. `#[test]` 重复 + 夹 doc 注释 → duplicated attribute（×3，service/types/provider）。
9. 前端 `Number('') === 0` 空串静默提交 → trim 判断。
10. web_search 判定 OR 过宽 / 归一化补名大小写 key 错过内置表 → 判定单一口径 + 补名用表 key。

## 11. 会话卫生（v2 补充，2026-08-16）

- 单会话不超一天：大任务按波次开会话；压缩后第一动作 Read 状态文件恢复。
- 每波结束同步六件套（STATUS/CURRENT/CONTEXT/ISSUES/DONE/state）——压缩后只有落盘的东西一定回来。
- 决策落地即记：新决策（做/砍/改方案）进 ISSUES.md (d)，被取代的条目标 superseded 而非删除（保留决策史）。
- trust-then-verify：agent 说"完成"先信但必核（L4）；空返回 = 失败重派；环境验证不了就说验证不了（虚报验证是红线）。
- 多会话并发：线上配置类操作错峰（实测踩踏教训）；文件按边界划分，同文件任务串行。
