# Kiro 车队 — 生产级运营化路线图

日期：2026-08-06
状态：进行中（G1 起逐项推进）

## 一句话

把车队从"能跑的功能"做成"能运营的产品"：角色权限、运营看板、审计可视化、规则可配、
全程非侵入。

## 硬约束（每一项改动都必须满足）

1. **非侵入**：只允许**新增**。不改 KiroStudio 核心业务逻辑——不动调度选号、
   不动鉴权链、不动转发路径、不动既有 API 的响应契约。
   - 允许：新增文件、新增结构体字段（带 `#[serde(default)]`）、新增路由、
     新增配置项（默认关闭）
   - 禁止：修改既有函数的行为、改既有字段语义、删既有字段、动 `/v1` 与 `/api/admin`
     既有端点的返回结构
2. **默认关闭**：任何新能力的配置默认值必须保持"升级后行为不变"。老部署不做任何
   配置时，观察不到差异。
3. **每项都验证**：单测 + 变异注入（确认测试会红）+ 镜像内端到端。缺任一项不算完成。
4. **生产零影响**：8990 全程 v16 不动。所有验证在 8991 试用容器。

## 为什么需要这些

当前车队的空白处不是功能少，而是**没有运营手段**：

- 所有 portal 用户完全等价。没有角色概念，管理只能靠 adminApiKey 全权操作，
  无法把"充值"授权给运营人员而不给他删库的权力。
- 审计表 `portal_audit` 已经在记 20 多种动作，但**没有任何界面能看**。
  出问题时只能进容器 sqlite3 手查。
- 规则只能改配置文件重启。价格、名额、注册开关都无法在界面上调。
- 没有任何运营视角的聚合：谁欠费、哪辆车最热、今天发了多少票、异常登录在哪。

## 任务序列

每项独立可发布，按依赖排序。`goal` 命令每次推进一项。

### G1 — SQLite 迁移机制（基石）

**为什么先做**：`init_schema` 只有 `CREATE TABLE IF NOT EXISTS`。已存在的库加不了列——
G2 的 `role` 列、G4 的看板索引全都卡在这里。没有迁移机制，任何加列的改动
在老部署上都是静默失效（表已存在 → 不建 → 读列报 no such column）。

**做什么**：新增 `src/portal/migrate.rs`。`user_version` PRAGMA 记版本，
逐级 ALTER。幂等、可重入、失败不留半个状态。

**验证**：用旧版 schema 建库 → 跑迁移 → 断言新列存在且老数据完好；
重复跑两次结果一致；变异（跳过某一级）必须红。

**实际实现与本节的偏差（如实记录）**：
- 落在 `store.rs::migrate` 而非新建 `migrate.rs`。迁移只有一张 `MIGRATIONS`
  常量表加两个私有函数，单独开文件反而要把 `has_column` 暴露成 `pub(super)`，
  扩大了可见性却没换来任何隔离。等迁移项多到需要分组时再拆。
- **不用 `user_version` 而用 `PRAGMA table_info` 探测实际列。** 版本号方案要求
  "每次改 schema 都记得递增版本"，漏记不会有编译错误，而漏记的表现是老库永远
  停在旧版本、缺列照旧。探测实际列是自校验的：列在就跳过、不在就补，与任何
  版本号是否准确无关。代价是每次开库多几个 PRAGMA 查询（微秒级，仅启动一次）。
- 已完成的验证：3 个测试（全新库有列且默认 `user`／手工建的老库+老数据迁移后
  role 为 `user`／连跑三次幂等），2 处变异（删掉迁移项、默认值改 `admin`）
  确认均变红后完整还原。

### G2 — 角色与权限

**做什么**：`portal_users.role` 列，三档 `admin` / `user` / `readonly`。
- `admin`：可进 portal 内的管理页，能充值/禁用/改密
- `user`：现有行为不变（看车队、上车、看钱包）
- `readonly`：能看车队和自己的钱包，**不能上车**（用于演示账号、审计账号）

新增 `/portal/api/admin/*` 一组端点，走 portal 会话 + role 校验，与现有
`/api/admin/portal/*`（走 adminApiKey）并存而非替代。

**为什么并存**：adminApiKey 是"部署者"的权限，portal admin 是"运营者"的权限。
把运营授权给一个 portal 账号，不必把 adminApiKey 交出去。

**首个 admin 怎么产生**（已决策）：**由 `adminApiKey` 持有者授予**，即
`POST /api/admin/portal/users/{id}/role`。不做"配置项指定用户名"也不做
"第一个注册的人自动是 admin"：

- 配置项指定用户名要求那个用户已经存在，否则配置静默失效；且改配置要重启。
- "第一个注册的人自动是 admin"在注册通道开放的部署上是一个提权漏洞——
  抢注即得管理权。
- KiroStudio 的管理者本来就持有 `adminApiKey`，那把钥匙的权限**严格大于**
  portal admin（它能改配置、增删凭据）。用大权限授予小权限，不引入任何新的
  信任根，也不存在"谁来授予第一个人"的循环。

**验证**：三档角色 × 每个端点的矩阵测试；越权必须 403 且不泄漏数据；
默认 role 为 `user`（老用户升级后行为不变）；readonly 上车必须被拒且**不扣分**。

**实际实现与本节的偏差（如实记录）**：
- **`/portal/api/admin/*` 这组端点本轮没做。** 已落地的是：角色类型、存储层、
  `POST /api/admin/portal/users/{id}/role`（adminApiKey 侧授予角色）、以及
  readonly 的两道闸门（不能上车、不能看明文）。让 portal admin 自己能在
  portal 页面里管用户，属于「运营者自助管理」，与 G3 的看板同属一个界面，
  合并到 G3 一起做更合理——否则要为它单独做一遍页面骨架。
- **`can_reveal_plaintext` 与 `can_board` 是两个方法**，尽管目前答案相同。
  合成一个的话，日后想放开「只读角色能看明文但不能花分」就必须先把它们拆开，
  而拆的时候很容易只改一处调用点。
- **加了 `tower` 作为 dev-dependency**（详见下方「验证教训」）。

**本轮的验证教训（重要）**：
第一次注入三个变异时**全部没有变红**，1014 个测试照旧全绿。原因各不相同：
1. `gate_plaintext` 的辅助函数 `gate()` 把 `can_reveal` 硬编码成 `true`，
   于是主安全断言从不走 `false` 分支。
2. `board` handler 的闸门在 async handler 内，而当时**没有任何测试能发 HTTP 请求**
   到它——纯函数测试与「闸门是否被接上」完全无关。
3. `admin_api` 同样没有 router 级测试，`set_role` 的最后管理员保护无人触达。

修法：给 `gate()` 加角色维度穷举（16 种组合）、加 `tower` dev-dependency 后写
`oneshot` 真实 HTTP 测试（board 三档角色 + set_role 8 个用例）。重跑三个变异
全部变红。

**这条教训值得记住**：权限系统的价值全在「越权请求真的被拒」，那是 HTTP 层的
事实。只测被 handler 调用的纯函数，等于测了锁的构造而没测门是否装上了锁。

**第二个教训（截图救的）**：我给 `gate_plaintext` 新增了 `key_kind = "forbidden"`，
但**忘了在页面里加对应分支**，于是只读账号的车票列落到默认分支、显示
`it.maskedKey`——5 行全是同一个 `ksk_DEMO...cdef`，还丢了指纹。

这不是明文泄漏（`maskedKey` 是前 8 + 后 4，中间 21 字符省略，复原不出真实
key，API 返回的 `key` 字段确实全是 `null`），38 条 API 断言也全都通过了——
**因为它们检查的是 `key` 字段，而 bug 在 `keyKind` 的渲染上**。只有截图看到
「5 行长得一模一样」才发现。

修法有两层：页面加 `forbidden` 分支（显示「只读账号不可见」+ 指纹），以及加一条
**结构性测试** `every_server_key_kind_is_handled_by_the_page`：扫 `http.rs` 里
`gate_plaintext` 返回的全部 `key_kind` 字面量，逐个要求页面脚本有对应分支。
注入变异（删掉页面的 `forbidden` 分支）确认它变红。

这条测试的意义是：**日后再新增 key_kind，忘了改页面会在 `cargo test` 时就红**，
不必等到有人截图。

### G3 — 运营看板

**做什么**：`/portal/api/admin/dashboard` + 页面区块。聚合：
- 今日/累计：发票数、充值总额、消费总额、退款总额
- 车辆热度：每把 key 的乘客数、单价、总收入，按热度排序
- 用户分层：欠费（余额 0 且有上车）、活跃、僵尸（注册未上车）
- 异常：近 24h 登录失败次数 top、被限流的 IP

**验证**：每个聚合数字都用独立 SQL 复算比对；空库时不崩、显示 0；
恒等式断言（发票数 == unlocks 行数、充值总额 == ledger topup 之和）。

**实际实现与本节的偏差（如实记录）**：
- **「被限流的 IP」没做。** 登录节流是**纯内存**状态（`http.rs` 的 throttle），
  没有落库，看板读不到。要做得先给它加持久化——那是改既有鉴权路径的行为，
  越过了「只新增」这条硬约束。本轮只做登录失败 IP 榜（审计表里有数据）。
- **`/portal/api/admin/*` 的骨架在本轮补上了**，这是 G2 有意推迟的那一项。
  `require_admin` 中间件叠在 `require_session` 之上（同一 Router 树里用
  `.merge` + 自己的 `route_layer`），会话校验仍然只有一处。
- **多了两块本节没写的内容**：管理员调账净额（`admin_adjust` 单列，可正可负），
  以及**账目自检**（`balance_sum == ledger_sum`、`balance == topup - spent`）。
  自检本来只打算做成测试，改为**算进响应、显示在看板上**——理由见下方教训。
- **`ledger_sum` 只统计在册用户的流水。** `portal_balances` 有 `ON DELETE
  CASCADE`，`portal_ledger` 故意没有外键（删号后仍要能回答「这个号花了多少」）。
  不过滤的话删任何一个有流水的用户都会让恒等式永久失衡，于是健康的库被报成
  账目异常——那样的自检会被当噪音忽略，比没有自检更糟。
- **「在册收入」不是历史收款。** 差额退款模型下 `paid` 会随新乘客上车被下调，
  所以 `SUM(paid)` 等于「此刻结算这辆车一共收了多少」。看板上写明了这一点，
  否则管理员拿它跟流水对不上会以为丢了账。

**本轮的验证教训**：
1. **自检做进产品，而不只做进测试。** 测试证明的是「这份代码在测试数据上自洽」。
   生产库经历过升级、并发、手工干预，而对账偏差的表现是「某个数字慢慢歪了」，
   **没有任何异常日志**。把恒等式算进响应，偏差在看板上第一时间可见。
2. **变异注入没真的注入，而报告显示全绿——本轮又踩了一次。** needle
   `ORDER BY COUNT(*) DESC, …` 含正则元字符 `(*)`，perl 替换匹配到 0 处，
   而测试照常 12 passed。此后每次注入都**先数 needle 出现次数（前后对比）**，
   数不对就不看测试结果。**未经确认的绿等于没测。**
3. **M5 真的注入后暴露了测试本身的弱点**：热度榜测试分不清「按乘客数排」和
   「按 credential_id 排」——因为热门那辆车恰好 id 更小。把数据反过来
   （热门车 id 更大）才让排序断言有意义，并补了次级排序键（最近上车时间）的测试。
4. **页面结构性测试有个洞，本轮补上了。** `every_js_id_exists_in_html` 只认
   字面量 `$('x')`，而看板把区块 id 当**实参**传进 `blk(id, title)` /
   `renderWindow(id, …)`——`blk('dash-typo')` 这种错字对它完全隐形。改为先找出
   「哪些函数会把形参喂给 `$()`」再扫调用点，且**追传递闭包**（`renderWindow`
   转发给 `blk`，隔了一跳）。第一版只追一跳，注入 `renderWindow('dash-typo')`
   时仍然全绿——这个假绿是靠变异发现的，不是靠读代码。
5. **新增 `every_dashboard_field_is_rendered_by_the_page`**：从 `store.rs` 的六个
   看板结构体抓字段名转驼峰，逐个要求页面读过。第一版用 `contains(".refund")`
   判断，被 `board()` 里的 `.refunded` 命中，删掉 `.refund` 的变异照旧全绿——
   **和 `no_dead_js_functions` 当年踩的是同一个子串陷阱**，改成按标识符边界判定。
   这条测试挡的是「服务端算了一个数、页面没渲染」：不报错、不留空格、截图也看
   不出少了什么，运营从此看不到那个数字。
6. **截图又抓到一个测试抓不到的东西**：热度榜的凭据 id 走了 `num()`，于是显示成
   `#9,001`——千分位是给「多少分」「多少人」这类**数量**用的，加在标识符上会被
   读成「9001 个什么」，还跟凭据管理页的 `#9001` 对不上（运营要靠这个号去那边查）。
   八条结构性测试全绿，因为它们查的是 id/类名/字段有没有被引用，而不是**格式对不对**。
   格式错误只能靠眼睛，这也是「改了 UI 就截图」这条规矩存在的理由。
7. **关掉开关那一屏，是截图救的第二处。** 服务端在 `portalCreditsEnabled=false` 时
   整条路由都不注册（返回 404，这是设计），而页面把它落进兜底分支显示
   「看板读取失败」，再配上六个**空的 `.blk` 边框盒子**——整屏看起来像页面塌了，
   而真实原因是一个管理员自己关掉的开关。API 层的
   `admin_dashboard_is_404_when_credits_disabled` 早就绿着：它断言的是状态码，
   而缺陷在**页面怎么解释这个状态码**。修法两处：404 单独成一个分支并写明开关名，
   以及六个区块套一层 `#dash-body` 容器，五条失败路径全部 `hideBlocks()`、
   `renderDash` 里显式打开（漏掉后者的话，失败一次之后重试成功仍是空白屏，
   而错误提示已被清掉，看起来像「点了刷新什么都没发生」）。
   注入一次故障再重试的往返已验证：失败时 0 个可见区块，重试后回到 6 个。
8. **`every_js_id_exists_in_html` 当场抓到了我自己的错。** 加容器时 HTML 写的是
   `dash-body`、JS 写的是 `dash-blocks`，`cargo test` 立刻红并点名那个 id。
   这正是本轮把它扩成「追形参传递闭包」的目的——若还是只认字面量 `$('x')`，
   这个错会以「看板一片空白 + 一句网络错误」的形式留到线上。
9. **两个失败的测试与本轮无关，已证明。** `token_manager` 的
   `test_credential_id_never_reused_after_purge` 与
   `test_delete_clears_per_id_cooldown_and_restore_is_clean` 用 `.invalid` 域名，
   而本机 DNS 把它劫持到 `198.18.0.x`，SSRF 防护如实拒绝。把全部改动 stash 到
   干净 master 后**这两条以同样的原因失败**，两个测试函数与 master 逐字节相同。
   这属于环境问题（DNS 劫持），不是回归。其余 1046 条全绿。
8. **「关掉开关」的回归测试必须也看界面，不能只看状态码。** 关掉
   `portalCreditsEnabled` 后 API 侧完全正确（路由消失、404、其余端点照常工作），
   但截图显示看板是「一句**看板读取失败** + 六个空边框盒子」——管理员会去翻数据库
   和日志找一个不存在的故障，而真实原因是他自己关掉的一个开关。修了两处：
   404 单独给一句「积分功能未启用（portalCreditsEnabled=false）」，以及把六个
   `.blk` 套进 `#dash-body`，任一失败分支（401/403/404/其它/网络异常）都整体隐藏，
   `renderDash` 成功时再显式打开（漏掉这一句的话重试成功后仍是一片空白，
   而错误提示已被清掉，看起来像「点了刷新什么都没发生」）。
   **完成定义里的「含关闭开关的回归」以前只理解成 API 层，这一条把它扩到界面。**
9. **`every_js_id_exists_in_html` 当场抓住了我自己的错。** 加 `#dash-body` 容器时
   HTML 写 `dash-body`、JS 写 `dash-blocks`，`cargo test` 立刻红并指名道姓。
   这正是本轮第 4 条扩展它的目的——而这次它挡的不是假想的未来错误，是十分钟前
   刚写下的真实错误。

### G4 — 审计 UI

**做什么**：审计表已有数据，缺界面。加筛选（按用户/动作/时间段）、
分页、明文脱敏展示、导出 CSV。

**验证**：注入各类审计事件后逐项筛出；分页边界（首页/末页/超界）；
导出的 CSV 不含任何 `ksk_` 明文。

**实际实现与本节的偏差（如实记录）**：
- **「明文脱敏展示」这一项本来就无事可做。** 查过全部 7 处 `add_audit` 调用点：
  `detail` 里只有计数、价格、角色变迁（`user -> admin`）和管理员自填备注，
  **审计表从来没存过明文 key**。本轮加了一条测试把这件事锁住
  （`audit_csv_never_contains_plaintext_key`），而不是加一层没有输入的脱敏函数——
  那种函数会让下一个人以为审计里有明文需要处理。
- **用户名筛选是精确匹配，不是子串搜索。** `LIKE '%alice%'` 用不上索引，而审计是
  全表最大的表之一（公网撞库持续写放大）；更要紧的是它有歧义：搜 `alice` 会把
  `alice2`、`malice` 一起捞进来，而审计要回答的是「**这个人**干了什么」。
  另给了 `actionPrefix`（前缀匹配）用于按动作族筛（`login_fail` 覆盖全部失败原因）。
- **多了一个 `/audit/actions` 端点**（动作及次数，供筛选下拉）。从库里查而不是
  返回代码里的常量清单：清单会漏掉新增动作，而漏掉的那个恰恰最需要观察。
- **新增两个索引**（`idx_portal_audit_user`、`idx_portal_audit_action`）。
  `CREATE INDEX IF NOT EXISTS` 在 `init_schema` 里，每次开库都跑，老库升级即得。
- **导出上限 5000 条，分页上限 200 条。** 无上限的导出等于一个 GET 就能让服务端
  把整张表拼成字符串驻留内存——不需要任何权限升级的放大路径。
- **CSV 公式注入防护**：以 `=`/`+`/`-`/`@`/Tab/CR 开头的字段前加单引号。这不是
  CSV 规范的一部分（任何 csv 库都不做），是 Excel 的行为。这条风险是**存储型**的：
  注册一个叫 `=cmd|'/c calc'!A0` 的用户名，运营双击导出文件就在自己机器上执行命令。
  选择加前缀而不是删字符——审计的价值在于如实记录，改掉原文事后就对不上账。

4. **`r#"…"#` 被 `href="#"` 提前终结。** 加导出链接时整页 HTML 常量在那一行断开，

   改用 `r##"…"##`：这比「把这一处 href 换个写法」更彻底，因为页面里任何位置
   将来再出现 `"#` 都不会再炸（HTML 里 `href="#"` 是极常见的写法）。
   **这是本轮唯一由编译器抓到的问题，其余都得靠测试或截图。**
5. **端到端验证发现我的 CSV 注入测试挑错了样本。** 单元测试用
   `=cmd|'/c calc'!A0` 当恶意用户名——但**注册接口根本不接受这个名字**
   （用户名校验只允许字母/数字/下划线/连字符/点），所以那条测试验证的是一个
   进不了库的值。在 8991 上逐个试过之后发现真实可达的向量是**连字符开头的
   用户名**：`-2-2`、`-minus-lead`、`-1e2` 全部注册成功，而 `-` 正是 Excel 的
   公式起始字符之一（`-1e2` 会被算成数字，`-2-2` 会被算成 -4）。
   已补一条专门用这类「注册器真的会放进来的」用户名的测试，并注入变异
   （从危险字符表里删掉 `-`）确认它变红——而**原来那条测试仍然是绿的**，
   证明它确实漏掉了这一档。
   教训：**安全测试的样本必须是能真正走通入口校验的值**，否则测的是一条

     `AUDIT_Q` 一直是进屏时冻结的那份空条件——**筛选框填了也不生效**，

   `every_module_level_state_var_is_declared`：扫全大写状态变量的使用点，

7. **登录节流在端到端验证里反复挡住我自己**（60s 起、指数退避到 30 分钟）。

   再执行。

   且跨重启持续**——是我自己 16 分钟前留下的一个后台 `until` 循环在用旧密码轮询，
   每次失败都把指数锁定重新翻倍。**审计表本身成了排查工具**（这也是它的用途）。

**G4 复查（交付后自查发现的 6 条，已全部修复）**：

1. **导出会静默截断。** 保留上限 `MAX_AUDIT_ROWS=5000` 与导出上限
   `AUDIT_EXPORT_MAX=5000` 看着对齐，但 `trim_audit` **每 6 小时才跑一次**，
   两次裁剪之间行数可以远超 5000。服务端**知道**被截断（`audit_page` 返回
   `has_more=true`），而导出 handler 只取 `page.rows`，把 `total`/`has_more` 丢了。
   于是运营下到 5000 行、以为那就是全部，再拿它去核对账。
   列表页有分页条兜着（「1–50 / 共 8000 条」），导出这条路上此前**没有任何提示**。
   修法是三个面同时给信号，因为它们各自都有盲区：CSV 正文末尾追加一行
   `#,,,,,"本次导出被截断：共 N 条…"`（「双击打开」时唯一看得见的地方）、
   响应头 `x-audit-total` / `x-audit-truncated`（脚本化调用不必解析 CSV）、
   文件名加 `-truncated` 后缀（存档后仍分辨得出这份完不完整）。
   尾注写**末尾**而不是开头：开头插一行非表头内容会让 Excel 的导入向导整列错位。
2. **`actionPrefix` 后端做了、前端点不到。** store 与 HTTP 层都支持，有 5 条测试
   覆盖，但 `readFilters()` 从不读它、HTML 里也没有输入框——只有 API 调用者用得上。
   我上一轮把「按动作族筛」当已交付能力写进了本节，那句话对 API 成立、对界面不成立。
   已补输入框；并补测试 `every_audit_filter_param_is_reachable_from_the_page`：
   从 `AuditParams` 结构体抓字段名、snake→camel 后逐个要求 `auditQs` 发送且
   `readFilters` 读取（`offset`/`limit` 豁免，它们由翻页按钮和「每页」下拉给）。
   **新增筛选维度若只做后端，这条测试会直接红**——这正是本条缺陷的形态。
3. **审计的读取与导出本身不留痕。** 明文外显会写 `reveal_keys`，但把**含每个用户
   完整 IP** 的审计表导出成文件，一条记录都不写。管理员可以把整份审计带离系统，
   而审计里没有这件事发生过的痕迹——审计不覆盖对审计自身的访问，是原则性缺口。
   已加 `admin_audit_export` 动作，detail 记
   `exported=N total=M truncated=bool filter=…`。
   **只记「某人导出了审计」而不记筛选条件是不够的**：事后要回答的是「他带走的是
   哪一批」。写审计失败不让导出失败（导出是读操作），但会打 error 日志。
4. **`until_ms` 闭区间碰上 `datetime-local` 无秒精度。** 输入框粒度是分钟，
   用户选「到 22:00」发出的是 `22:00:00.000`，而 SQL 是 `at_ms <= untilMs`，
   于是 `22:00:30` 的记录被排除——**最多静默漏掉 59.999 秒**，且毫无迹象。
   已加 `localToMsEnd()`：无秒（长度 ≤16）补 59999ms，有秒补 999ms。
   起始时间**不补**（下界的语义本就是「从这一刻起」）。实测验证：
   `22:00:30` 现在落在窗内，`22:01:00` 仍在窗外。
5. **我上一轮对索引的说法不准确。** `EXPLAIN QUERY PLAN` 实测：前缀筛的
   `action LIKE ? ESCAPE '\'` 走的是 `SCAN portal_audit USING INDEX
   idx_portal_audit_at`（**全表扫**），改写成 `action >= ? AND action < ?` 才会
   走 `idx_portal_audit_action` 的覆盖索引。但**没有改**，因为两者语义不等价且
   差异对使用者不可见：SQLite 的 `LIKE` 对 ASCII **大小写不敏感**，范围比较
   （BINARY 排序）是敏感的——实测 `LIKE 'login%'` 会匹配 `LOGIN_UPPER`。
   生产写入的动作名全是小写 snake_case（核对过全部 17 个字面量），所以对现有数据
   无差别；但筛选框里的前缀是**人手打的**，有人输入 `Login` 时两种写法结果不同。
   5000 行规模下全表扫是微秒级，不值得用一个不可见的语义变化换测不出的性能提升。
   已把实测结论写进注释：那个索引服务的是**精确**动作筛选和 `audit_actions` 的
   GROUP BY，前缀筛确实不走它。
6. **同一张表两个读取路径。** `recent_audit`（无筛选/分页，adminApiKey 侧的
   `/api/admin/portal/audit` 在用）自带一份 `SELECT … ORDER BY at_ms DESC, id DESC`，
   与 `audit_page` 并存。两份 SQL 眼下一致（逐字核对过），但一致是靠人核对维持的：
   日后给 `audit_page` 的排序动一次刀，这一份不会跟着走，两个入口会对「最近 20 条
   是哪 20 条」给出不同答案，而两边各自看都自洽、没有一处报错。
   已改为转调 `audit_page`。**改完立刻踩到一个自己造的回归**：`audit_page` 把
   limit 钳到 `[1, MAX]`（对分页是对的，`limit=0` 会让界面空白而不报错），
   于是 `recent_audit(0)` 从「0 条」变成「1 条」。眼下无调用方传 0，属**潜伏**差异
   ——等到有人写出 `recent_audit(n)` 而 n 可能算出 0，那多出来的一条会被当成真实
   数据。已在转调前加 `if limit == 0 { return Ok(vec![]) }` 并补测试锁住。
   **教训：等价重构也要问「哪个输入会让新旧行为分叉」，而不是只看现有测试是否全绿。**

**复查一轮又抓到的第 7 条（写代码时自己引入的）**：`describe_filter()` 空条件分支
返回 `"filter=none(all)"`（自带前缀），非空分支返回 `"username=x"`（不带），

是在**读端到端输出**时看见的，不是测试报的。已统一为两个分支都不带前缀，
并补测试 `describe_filter_never_carries_its_own_prefix` 同时锁住两个分支。

### 为什么 API 是 `no-store` 而不是 `no-cache`

`no-cache` 的语义是「**可以存**，但用前须回源验证」——明文 key 已经落盘了。
而 `/portal/api/keys` 在积分关闭或用户已上车时确实会下发明文 `ksk_`（`gate_plaintext`）。
更要紧的是「没有指令」不等于「不缓存」，而等于「由缓存方自己拿主意」（RFC 9111 §4.2.2）：
一旦前面挂了 nginx / CDN / 公司出口代理，这类响应是**允许进共享缓存**的，那就是跨用户串号。

附带 `Pragma: no-cache` + `Expires: 0` 兜住不认 `Cache-Control` 的上古代理。
`insert` 而非 `append`——两个矛盾指令并存时行为取决于缓存实现挑哪个，而挑错的那一侧
是「明文被 CDN 存一年」。

### 为什么做成中间件

逐个 handler 加有个确定的失效模式：**日后新增端点必然漏**，且漏掉不会有编译错误、
不会有用例变红，表现是新端点悄悄变成可缓存的。装在路由树上意味着新增路由自动继承。
另有 `every_portal_api_route_is_declared_no_store`：从 `create_router` 源码里抓出全部
`/portal/api/` 路由逐条打真请求，新增路由自动进入检查。

### 结论为「无需改动」的部分

- `balance_cache`（`admin/service.rs:162`）：拉取 TTL 300s、展示保留 7 天、落盘、
  删号与彻底删号都清条目。关键是**凭据 ID 不复用**（`token_manager.rs` 单调 `fetch_add`，
  启动时还 `fetch_max(max_trash+1)`），所以不存在「新号读到旧号余额」的串档。
- `BG_POOL`：上限 20，且有 generation 计数器处理「关掉 R18 后在途请求仍可能入池」的竞态。
- `assets/` 的 `immutable, max-age=1年`：31 个文件全部带 8 位内容哈希，策略与命名配对正确。
  已加 `year_long_immutable_is_only_used_for_content_hashed_assets` 钉住这个配对。
- `vite.svg` 在顶层无哈希、落到 `max-age=3600`：改图标后最长 1 小时不一致，会自愈，不管。

### 一个又踩到的坑：靠正则判断「文件名有没有内容哈希」

`year_long_immutable...` 第一次跑就红了，说 `overview-page-C-63v8Th.css` 没有哈希。
实际是我的判据错了：vite 用 **base64url**，哈希本身可以含 `-`，而我按「最后一个 `-`
之后」切，等于切进了哈希内部。改成「取 stem 末 8 个字符 + 前面必须紧跟 `-`」才对。
同一个错我在这次排查里犯了两次（先用 grep 判断时也误报过三个文件）——**对文件名做
结构判断时，先拿真实样本对齐，别信第一版正则。**
