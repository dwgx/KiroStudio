# 深度推理：平摊分流体系研究（选号均衡）

> 状态：研究文档（只读结论，不构成已实施改动）。2026-08-16。
> 范围：Kiro 主路径 12 位排序键（`select_next_credential`，token_manager.rs:3700-3990）
> 与透传池 5 键（`select_custom_api_inner`，token_manager.rs:3308-3344）的对比、
> 平局语义、各维度质量、平摊公平性、垃圾代码与根治方案。

## 0. 结论摘要

1. **min_by_key 平局不是随机器，是确定性偏斜。** 候选集是 `Vec<&CredentialEntry>`
   （源自 `entries: Mutex<Vec<CredentialEntry>>`，token_manager.rs:2018），Rust std
   `min_by_key` 对相等键保留第一个元素 ⇒ 全平局时**恒选 Vec 下标最小的号**（= 最早
   创建的号，id 单调递增 :8292）。**没有 HashMap 迭代序随机性。**
2. **两池差距真实存在但被高估了。** 透传池缺的 12 键中，`unusable`/`health_tier`/
   `neg_p_fine` 缺得有理（隔离铁律，透传无 health/熔断概念）；**真正的缺口只有
   `starved`（反饥饿）一个**——透传池低负载（请求间隔 >60s，RPM 滑窗归零）时恒选
   同 priority 层内第一个号。线上 4 通道全是透传池，这是当前线上的实际偏斜源。
3. **惊群窗口已封死。** 两池占位（`InflightGuard::acquire` + `rpm.record`）都在
   `entries` 锁临界区内（主路径 commit_selection :4088-4091；透传池 :3364-3380），
   W10 的 guard 提前 drop 问题在透传池 :3219-3223 与 provider.rs:761-772 已文档化并
   由调用方持有。无残余记账窗口。
4. **高负载号被冷落是保护不是饥饿**（RPM 饱和硬门 + 已用率排序）；全 0 时的均匀
   由 `starved`（主路径）与 inflight/rpm 记账（两池）兜住，主路径每号每 180s 至少
   一轮，均匀性可接受。
5. **垃圾代码量很小**：2 处注释漂移（health.rs:248、provider.rs:765）、1 处公式复制
   （ramp_tier 两处实现逐字相同）、双份维护的排序键概览注释（有同步纪律，风险低）。
6. **根治推荐**：透传池补 `starved` 键（唯一中等收益改动）；排序键统一**不推荐**
   （隔离铁律 + 读 health 有写副作用）；tie-break 显式化 `e.id`（零回归、纯契约化）；
   RPM 周期性豁免**不推荐**。

## 2. min_by_key 稳定性与平局语义

### 2.1 事实

- 候选集：主路径 `selectable: Vec<&CredentialEntry>`（:3605-3608），透传池
  `candidates: Vec<&CredentialEntry>`（:3250），均派生自 `entries: Mutex<Vec<...>>`（:2018）。
- `entries` 顺序：创建序（push 追加 :8472/:8673/:8867），删除用 `Vec::remove`（:8593）
  保持相对序，恢复 push 尾部。id 由 `next_id.fetch_add(1)` 单调分配（:8292），
  id 序 = 创建序 = 下标序（恢复的号除外：id 大、下标也大，一致）。
- Rust std `Iterator::min_by_key` 用 `<` 比较，**平局保留第一个遇到的元素**。

### 2.2 结论：确定性偏斜，不是随机器

全平局（新池全 0：全健康/全 0 在途/无 RPM 样本/无模型计数）时恒选下标最小的号。
任务描述中"= HashMap 迭代序随机"的假设**不成立**：没有 HashMap 迭代序参与排序。

**这算好还是坏？**

- **确定性本身是资产**：选号在 entries 锁内串行（一次一个），无并发冲突；确定性让
  行为可复现、可测试（现有测试 :14217 断言"3 个号 6 次应各 2 次"依赖平局后的轮转）。
  随机 tie-break 的唯一收益（防可预测性）在网关场景无价值——不存在恶意竞猜选号。
- **但依赖 Vec 下标是隐式契约**：平局胜者 = "最早创建且未被删除的号"，语义藏在
  `entries` 的维护细节里，不是排序键的显式声明。删除/恢复/重排会静默改变平局胜者。
- **偏斜的实际影响已被兜住**：平局只存在于"全 0"瞬间——第一个请求被选后
  `rpm.record` + `InflightGuard` 立即使 ⑦ 位分出高下；主路径另有 ② starved 保证
  每号每 180s 至少一轮。真正受害的是**透传池低负载**（见 §4.2）。

### 2.3 平局链的完整性

主路径 12 位键在"全 0"时全部相等，最后一位 `success_count`（u64，全 0 时也相等）
不能打破 ⇒ 平局落到迭代序。**没有"永不相等"的键存在**——这是设计上可接受的
（任何有限键集都可构造全平局输入），但要承认：平局兜底 = Vec 下标，而不是某个
排序键。方案 T1 把它显式化为 `e.id`。

## 3. 各维度质量评估

### 3.1 inflight 维度（⑦ 位）与惊群窗口

- 占位点：主路径 `commit_selection`（:4388-4406），透传池内联（:3364-3380），
  均在 entries 锁内 ⇒ **选号与占位原子**，后续并发选号（排队等锁）看到已占位的
  inflight ⇒ 惊群被结构性消除（先到先占，后到分流）。
- W10 修的是"guard 提前 drop"：透传池 :3219-3223 明确警告 `let (id, cred, _) = ...`
  会废掉修复；provider.rs:761-772 文档化 `CallMeta.inflight` 随响应流存活。已确认
  调用方持有，无残余。
- **残余候选窗口**：`peek_only` 探测（:3352-3355）与真实选号之间（provider 闸门
  peek 后释放锁，真实选号重新加锁）——peek 的"有候选"决策可能过期（候选被并发
  请求占用）。后果仅是 failover 提前/延后一跳，**不是记账窗口**（peek 不占位，
  :3345-3351 明确），不算缺陷。
- 一处结构性边界（有文档，非 bug）：`is_sticky_reuse_healthy` 的半开概率放行
  （:4526-4528）用 `fastrand::f64()` —— 该函数一次请求只调一次（只判 current_id
  一个号），注释 :4509-4511 说明了为何不会造成同轮自相矛盾。这是全仓排序路径上
  仅存的随机项，且**不在排序键内**。

### 3.2 slot_pressure_permille（⑨）与 rpm_usage_permille（⑩）

- 均为整数千分比（规避浮点比较不确定性，:3864-3868/:3831），除零由
  `effective_saturation_limit` 恒 >0 保证（:4444-4454）。
- ⑨ 的分母是**该号自身容量**（纵向自身余量），⑩ 是 RPM 已用率按容量归一；注释
  :3859-3862 论证与自适应 LOAD_REF（池平均横向归一）不构成同一信号二次放大——成立
  （信息源不同、落位不同）。
- ⑨ 可超 1000‰（inflight 无界，真并发可远超 rpm_limit），超界不影响升序语义。
- **口径统一点**：两键的容量均来自 `effective_saturation_limit`（含 headroom 折扣），
  与饱和硬门同一真相源（:3790-3794）——无漂移。

### 3.3 neg_p_fine（⑪）

`-((p_weighted * 1000.0) as i64)`（:3838）。p_weighted = p_avail × balance_factor，
p ∈ [0,1]，factor ∈ [0.5,1.0]（floor 映射 :5983-5986）⇒ neg ∈ [-1000, 0]。

- 精度 0.001，作为**末位兜底**足够：它只在 ⑦⑧⑨⑩ 全平局时生效，0.001 以下差异
  落到 ⑫ success_count，无实质损失。
- `as i64` 向零截断保持单调（p 大 → neg 更负），无比较破坏。
- **数值设计合理**。余额加权只作用于此位、不掀翻 0.7.23 分流（:3833-3835），
  注释与实现一致。

### 3.4 health_tier（④）与分层阈值

- 阈值 0.75/0.40（health.rs:168-169），宽边界降抖动（:166-167）。
- **一个值得记录的边界交互**：`HEALTH_429_WEIGHT=0.6` + `A_429=0.5` ⇒ **单次 429
  就把 ewma_429 从 0 抬到 0.5**，health = 1×(1-0.6×0.5) = 0.7 < 0.75 ⇒ **一次 429
  即掉出 healthy 档**（health.rs:30, 363）。这是"429 敏感"的刻意设计（A_429 快升，
  :29），且 degraded 档仍有流量（档 0 饱和/在途高时溢出），加上 starved 180s 探测
  兜底，不会自锁。结论：合理，但"一次 429 即掉档"值得在运维文档中说明，否则面板
  上"健康档跌落"会显得过于敏感。
- 档位用**原始 p**（不含余额加权，:3820）：余额不该把健康号打进坏档——正确。
- 熔断 gate 是硬门（p_avail=0 直接进 ① unusable），health_tier 只是软权重，分层
  不会绕过熔断（有回归测试 :1020-1041 守）。

### 3.5 ramp_tier（⑤）质量

- 实测依据充分（scheduling.rs:179-194：≥5x 跃升 48.3% 429 vs 平稳 0.7%）。
- 样本门槛 `RAMP_MIN_SAMPLES=20`（:2242-2247）防新号/低负载误伤。
- 排序键而非硬门（:3919-3921）：单号池/全池爬坡时不制造网关 503——正确取舍。
- 排在 inflight 之前（:3923-3925）：失败快（~1s）的号 inflight 反而低，先排 inflight
  会正反馈选中最被暴打的号——论证成立。
- **唯一问题**：公式两处复制（§5.2）。

## 4. 平摊公平性

### 4.1 分身（clone）的平摊

- `family_key`：clone_group → `clone:{group}`（user_id.rs:24，credentials.rs:947）。
- 冷却族级连坐：`report_suspicious_activity` 计数取族内 max、整族共用、整族禁用
  （:6263-6296）；health 族级连坐：`report_family_suspicious` 整族 Open（:6340-6345）。
- **RPM 无族级维度**：`rpm.record`/`rpm_usage_permille`/饱和硬门全部按单分身 id。
  同一上游账号的 N 个分身各自独立记账 ⇒ 上游账号真实速率 = 族内之和，而分流按
  单分身容量。5 分身各 20 RPM（各自 < 30 fallback）⇒ 上游被灌 100 RPM 而无任何
  单分身判定饱和。
  - 这是**设计空隙还是缺陷**取决于上游语义：若 clone_group 分身上游 key 独立
    （每分身一个 key），按分身记账正确；若共享同一上游 key，族内 RPM 应联合限额。
    `family_key` 把限流/健康设为同族 ⇒ 说明作者认为它们是"同一上游账号" ⇒ RPM
    维度不一致。**建议核实上游 key 独立性后决定**（若共享 key，族级 RPM 联合
    饱和是中等收益改动；若独立，现状正确，只需在文档钉死）。
- 排序键内 family_key 只用于 health 查键（:3789），clones 的 health_tier 相同、
  其余维度独立 ⇒ clones 之间按负载平摊正常。

### 4.2 高负载号保护 vs 饥饿；全 0 时是否均匀

- **保护成立**：主路径 rpm 高 → ⑩ rpm_usage 高排后 + 第一趟饱和硬门剔除
  （:3991-4003）；透传池 rpm 高 → 第 3 键排后（无硬门，failover 排除集兜底）。
  这是保护（防上游 429），不是饥饿。
- **饥饿的反向风险**：容量**配置错**的号（rpm_limit 设低）恒饱和恒沉底，starved
  排在 unusable 之后（:3906-3908）不救它——**刻意的**（饱和号不该接），但配置
  错误无法自动识别，流量压向其余号。这是配置责任，不是调度缺陷。
- **全 0 均匀性（主路径）**：全 0 时首请求恒选 idx0，占位后 ⑦ 立刻分流；低负载
  （RPM 滑窗 60s 归零）时靠 ② starved（180s）轮转 ⇒ **每号每 180s 至少一轮**。
  52 请求实测 6.67x 偏斜（:3879-3890）已被 starved 结构性兜住（作者 :3871-3875
  的结论与代码一致）。严格来说非均匀（idx0 每轮略多，因它是周期内第一个到期者），
  但量级从 6.67x 降到 ~2x/N，可接受。
- **全 0 均匀性（透传池）**：无 starved ⇒ **请求间隔 >60s 时每轮全平局恒选 idx0**
  （同 priority 层内）。低负载多号透传池：idx0 独吞全部流量，其余号零流量。
  **这是当前线上（4 通道全透传）的真实偏斜源**——好在 priority 键通常让"主通道
  优先"成为预期语义；但当多个同 priority 号并存时（如多个备用通道同 priority），
  后列号长期饥饿。

### 4.3 透传池 5 键在"多模型混发"下的平摊

- `model_calls`（第 4 键）按模型计数 ⇒ 模型 A 的流量只摊 A 的计数，模型 B 独立
  摊 B ⇒ 多模型混发下每个模型各自均摊。**维度够用**（与主路径 ⑧ 同构）。
- 总 rpm（第 3 键）混全模型 ⇒ 模型 A 猛灌抬高各号总 rpm 后，模型 B 的请求会选
  "总 rpm 最低"的号 = A 没打过的号 ⇒ 总负载均衡自然成立。
- 缺容量归一（⑨⑩ 同款）在混发下同样存在：大容量号按裸次数摊，容量优势不体现。
  低优先级改进（同 §1.3）。
